Offerings

Seven offerings, one rule: measure before we touch anything.

Every engagement is fixed-price and starts from evidence. The Control Score sizes your system; its 90-day plan quotes exactly which offerings apply, in which order, and what each will cost.

How prices scale: a 30,000-line repo and a 2-million-line estate across 40 repositories are not the same product at different sizes, so we don't price them that way. Every quote is built from meters we measure at intake and print on the quote: a base fee per repository (the fixed overhead is real), degressive per-1,000-lines rates (our pipelines process volume at falling cost, and you get that back), and per-hotspot or per-ticket meters for safety and change work. Above roughly 3 repos or 250k lines, the entry point is the Estate Survey: triage first, depth only where it matters.

Control Score

FOR: CTOs AND ENGINEERING LEADERS WHO NEED THE HONEST PICTURE FIRST

A 48-hour audit that measures how much control you actually have over your codebase, computed deterministically from your repository and git history. No workshops, no questionnaires: the code and its history are the witnesses.

Six scored dimensions:

  • Knowledge risk - bus factor per module, weighted by how critical each module is. Named plainly: "4 of your 12 modules are effectively known by one person."
  • Change risk - hotspots where high churn meets high complexity: the ten files most likely to hurt you.
  • Safety - test coverage measured where change actually happens, not the vanity global number.
  • Currency - dependency freshness, end-of-life runtimes, open CVEs.
  • Legibility - documentation drift, dead code, naming consistency.
  • Exit cost - a euro estimate of what key-person loss and onboarding cost you, with the formula shown.

You receive a 15-page report your board can read, the raw metrics as JSON, and a 90-day recovery plan with priced next steps. Re-run the audit on the same commit and you get identical numbers - the analysis is reproducible, not vibes.

Many repositories? Start with the Estate Survey. A Control Score goes deep on one system (up to 3 repos, 250k lines). If your code is an estate - dozens of repositories, millions of lines - deep-auditing everything up front would waste your money. The Estate Survey instead triages the whole portfolio: a mini-score per repository (activity, bus factor, size, coupling), a map of how the repos depend on each other, and a depth plan that says which repos deserve full treatment, which need docs only, and which are dormant and just need to stay inventoried. Deep work is then quoted repo by repo, on evidence.

Capture

FOR: THE MOMENT A KEY DEVELOPER RESIGNS. THEIR NOTICE PERIOD IS THE WINDOW.

When the person who knows the system leaves, most of what they know leaves with them - unless it's extracted deliberately, fast, and verifiably. Capture does exactly that, in one to two weeks, using about four hours of the expert's time.

How it works:

  • We analyze the code first, then generate targeted questions, each anchored to something real: "in payment_retry.py, retries stop after 3 days and the constant is unexplained - why 3 days, and what breaks if it changes?" No "please describe the architecture."
  • Two interview sessions (or async written answers), transcribed.
  • Every answer is checked against the code where verifiable; the rest is recorded as testimony, attributed and dated.
  • The knowledge is written into your documentation where it belongs, next to the code it explains.
  • Questions that end up unanswered ship as a named risk list - knowing which nine questions now have no owner is worth money too.

Shield

FOR: SYSTEMS WHERE EVERY DEPLOY IS A GAMBLE

A safety net of characterization tests on your riskiest modules: tests that pin down what the code does today - including behavior that looks like a bug - so that any future change that alters behavior gets caught in CI before it reaches production.

What makes our shields real:

  • Targets are chosen by measurement: the hotspots from your Control Score with the least protection, approved by you with a per-target price.
  • Every suite is proven by mutation testing: we deliberately break your code in controlled ways and verify the tests turn red. A test that can't fail is theater; we prove ours can, and the mutation report is part of the delivery.
  • Contract tests guard the boundaries between modules, so teams stop breaking each other.
  • Everything ships as pull requests into your CI, in your test framework.

The Shield is also the precondition for everything that follows: we don't modernize or evolve code we haven't made safe to change. That rule protects your system and our fixed prices equally.

Evolve

FOR: NEW REQUIREMENTS ON A SYSTEM YOU CAN'T AFFORD TO REWRITE

The destination of the whole path: your legacy system starts moving again. New features and intentional behavior changes, delivered on the system itself, without the rewrite.

How it stays under control:

  • First, you receive the recovered specification of your system: a catalog of what it actually does, behavior by behavior, each entry backed by code evidence and pinned by a test. For most clients it's the first accurate spec they've had in years.
  • New requirements become behavior change tickets: behavior X becomes behavior Y, with acceptance criteria, a computed impact set, and a fixed price. You sign the list before work starts.
  • Every ticket starts with its acceptance test, written and failing, before any code changes.
  • CI blocks any change to a pinned behavior that no signed ticket covers. The difference between "bug" and "change" becomes contractual, and the arguments end.
  • After each ticket, the spec and docs regenerate. You review behavior diffs, not code diffs.
